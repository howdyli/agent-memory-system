## 3. 延迟基准（latency）

### 3.1 测试方法

对每类操作采样 N 次（默认 100，可通过 `PERF_ITERATIONS` 调整），含 10% 预热。使用 `time.perf_counter()` 计时，按最近秩方法计算 P50/P95/P99。

**数据规模梯度**：
- `small`  / 1k    — 1,000 片段（CI 友好）
- `medium` / 10k   — 10,000 片段（nightly）
- `large`  / 100k  — 100,000 片段（release / 手动）

**操作覆盖**（6 类）：

| 操作 | 实现入口 | 目标 P99 |
|------|----------|----------|
| 记忆召回（top_k=10） | `RecallEngine.recall` | ≤ 500ms |
| 语义搜索（向量） | `search_fragments_by_semantic` | ≤ 300ms |
| 混合搜索（4 信号融合） | `hybrid_search` | ≤ 800ms |
| 片段创建（含 embedding） | `create_fragment` | ≤ 200ms |
| 图谱邻居查询（depth=2） | `get_neighbors` | ≤ 300ms |
| 自动召回（auto_recall） | `auto_recall` | ≤ 1000ms |

### 3.2 通过条件

- 所有 6 项 P99 均达标
- 各操作错误率 ≤ 5%（否则即使延迟达标也判未通过）

### 3.3 运行命令

```bash
# CI 友好（1K 片段，100 次采样）
python -m app.benchmarks.runner run --suite latency --scale 1k

# nightly（10K 片段）
python -m app.benchmarks.runner run --suite latency --scale 10k

# release（100K 片段，需手动触发）
python -m app.benchmarks.runner run --suite latency --scale 100k

# 慢机器放宽阈值
PERF_SCALE=2.0 python -m app.benchmarks.runner run --suite latency --scale 1k

# 大样本降低抖动
PERF_ITERATIONS=500 python -m app.benchmarks.runner run --suite latency --scale 10k
```

## 4. 吞吐基准（throughput）

### 4.1 测试方法

并发度梯度：1 / 4 / 8（默认，可通过 `--concurrency` 或 `PERF_CONCURRENCY` 调整）。

**场景覆盖**：

| 场景 | 默认规模 | 说明 |
|------|----------|------|
| fragment_create | 1,000 条 | 并发创建含向量嵌入的片段，测吞吐 + Outbox 积压 |
| table_record | 500 条 | 并发导入结构化表记录 |
| conversation_extraction | 100 段 | LLM 路径抽取记忆（需 LLM，默认 `PERF_SKIP_LLM=1` 跳过） |

### 4.2 通过条件

取单并发（c=1）的片段吞吐量作为判定依据：
- `fragment_throughput_ops` ≥ 50 ops/s
- `fragment_success_rate` ≥ 95%
- `table_record_throughput_ops` ≥ 100 ops/s

### 4.3 关键观测点

- **吞吐随并发度的扩展性**：理想为近线性，受 SQLite WAL 写锁与 ChromaDB HNSW 写入开销约束
- **Outbox 积压**：`vector_outbox` 表 `pending` 数量反映跨存储一致性延迟。理想 < 50；> 500 提示向量同步落后
- **错误率随并发变化**：若 c=8 错误率 > 5%，提示锁竞争或资源不足

### 4.4 运行命令

```bash
# 默认（c=1,4,8，1K 片段）
python -m app.benchmarks.runner run --suite throughput

# 自定义并发度
python -m app.benchmarks.runner run --suite throughput --concurrency 1,4,8,16

# 启用 LLM 抽取场景
PERF_SKIP_LLM=0 python -m app.benchmarks.runner run --suite throughput

# 放大批量
PERF_FRAGMENT_BATCH=5000 python -m app.benchmarks.runner run --suite throughput
```

## 5. 负载基准（load_test）

### 5.1 测试方法

模拟 N 个并发 workspace（默认 10/50），每个 workspace 启动一个独立线程，按以下分布持续混合操作：

| 操作类型 | 占比 | 实现 |
|----------|------|------|
| 召回（semantic search） | 70% | `search_fragments_by_semantic(top_k=10)` |
| 写入（fragment create） | 20% | `create_fragment` |
| 图谱查询 | 10% | `get_neighbors(depth=1)` |

**持续时长**：默认 30s（CI），release 可设 600s。

**预置数据**：每 workspace 200 片段 + 20 图谱实体。

### 5.2 通过条件

取最大并发级别（默认 50 workspace）的结果判定：
- `success_rate` ≥ 99%
- `p99_ms` ≤ 2000ms

### 5.3 关键观测点

- **错误率随并发变化**：理想 < 1%。若 50 ws 错误率 > 5%，提示资源瓶颈
- **P99 抖动**：长尾延迟通常由 SQLite checkpoint 或 ChromaDB persist 触发
- **内存峰值增长**：`tracemalloc` 追踪 Python 堆增长，理想 < 100MB；若持续增长提示泄漏
- **操作分布均衡**：`op_breakdown` 检查 70/20/10 分布是否符合预期

### 5.4 运行命令

```bash
# CI 默认（10/50 ws，30s）
python -m app.benchmarks.runner run --suite load_test

# 自定义 workspace 数
python -m app.benchmarks.runner run --suite load_test --workspaces 10,50,100

# 长时负载（release）
python -m app.benchmarks.runner run --suite load_test --duration 600 --workspaces 100

# 环境变量方式
PERF_LOAD_WORKSPACES=10,50,100 PERF_LOAD_DURATION=120 \
  python -m app.benchmarks.runner run --suite load_test
```

## 6. 存储增长基准（storage_growth）

### 6.1 测试方法

对每个规模（默认 1K/10K）：
1. 拍摄存储基线快照（SQLite 文件 + ChromaDB 目录 + Redis 内存）
2. 写入 N 条记忆片段（含向量嵌入）
3. 触发 `VACUUM` 回收 SQLite 空闲页
4. 再次拍摄快照，计算增量

### 6.2 通过条件

取最大规模的每条平均成本判定：
- `avg_bytes_per_fragment` ≤ 5,000 字节（SQLite + ChromaDB 合计）

### 6.3 关键观测点

- **SQLite 增长**：含 8 张核心表 + 索引，WAL 模式下写放大可控
- **ChromaDB 增长**：HNSW 索引开销随片段数非线性增长，是主要瓶颈
- **Redis 增长**：仅 `@ttl_cache` 缓存命中条目，规模受 TTL 约束
- **每条成本随规模变化**：1K → 10K → 100K 应保持稳定；若显著上升提示索引膨胀

### 6.4 运行命令

```bash
# 默认（1K, 10K）
python -m app.benchmarks.runner run --suite storage_growth

# 含 100K（release）
python -m app.benchmarks.runner run --suite storage_growth --scales 1000,10000,100000

# 自定义规模
PERF_STORAGE_SCALES=5000,50000 \
  python -m app.benchmarks.runner run --suite storage_growth
```

### 6.5 结果模板

## 7. 性能回归检测

### 7.1 机制

`baseline.json` 存储性能基线，每次 nightly/release 运行后通过 `--check-regression` 自动对比：

| 指标类型 | 方向 | 回归判定 |
|----------|------|----------|
| 延迟（P99 等） | 越低越好 | 当前 > 基线 × (1 + 阈值%) |
| 吞吐（ops/s） | 越高越好 | 当前 < 基线 × (1 - 阈值%) |
| 成功率 | 越高越好 | 当前 < 基线 × (1 - 阈值%) |
| 存储（bytes/条） | 越低越好 | 当前 > 基线 × (1 + 阈值%) |

**默认阈值**（见 [baseline.json](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/baseline.json#L60-L66)）：

| 指标类别 | 阈值 |
|----------|------|
| 延迟 P99 | 20% |
| 吞吐 | 20% |
| 负载 P99 | 25% |
| 存储 | 30% |

### 7.2 运行命令

```bash
# 1. 首次基线化
python -m app.benchmarks.runner run --suite latency --update-baseline

# 2. 后续运行自动检测回归
python -m app.benchmarks.runner run --suite latency --check-regression

# 3. 对已有结果文件做回归对比
python -m app.benchmarks.runner regression \
  --input results.json --baseline baseline.json --output regression.md

# 4. 全 L3 层级运行 + 回归
python -m app.benchmarks.runner run --level L3 --check-regression \
  --output results/l3.json --report results/l3.md
```

## 9. CI 集成

### 9.1 周期调度建议

| 套件 | 触发 | 规模 | 预期耗时 |
|------|------|------|----------|
| latency | 每次 PR（L3 档位可选） | small (1K) | ~2 分钟 |
| throughput | nightly | c=1,4,8 / 1K 片段 | ~5 分钟 |
| load_test | nightly | 10 ws / 30s | ~1 分钟 |
| storage_growth | release | 1K, 10K | ~5 分钟 |
| 全 L3 + 回归 | release | 全规模 | ~30 分钟 |

### 9.2 失败处理

- **延迟未达标**：检查索引状态、ChromaDB persist 频率、SQLite WAL 配置
- **吞吐未达标**：检查 Outbox 积压、向量同步批大小、连接池
- **负载错误率 > 1%**：检查 SQLite 写锁超时、ChromaDB 并发限制
- **存储成本超标**：检查 ChromaDB HNSW 参数 `ef_construction` / `M`
- **回归告警**：先确认是否基线过期（环境变更需 `--update-baseline`），再排查代码改动
