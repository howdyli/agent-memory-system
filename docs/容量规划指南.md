# 容量规划指南

> 基于 L3 性能基线（[性能基准报告.md](file:///Users/howdy/pm/agent-memory-system/docs/性能基准报告.md)）的存储与吞吐特征，
> 给出 Agent Memory System 在不同业务规模下的资源规划建议。

---

## 1. 适用范围

本指南适用于以下部署形态：

| 部署形态 | 关系存储 | 向量存储 | 缓存 | 典型场景 |
|----------|----------|----------|------|----------|
| 单机开发 | SQLite (WAL) | ChromaDB (本地持久化) | Redis（可选） | 个人/小团队，< 10 万记忆 |
| 单机生产 | SQLite (WAL) | ChromaDB (本地) | Redis | 单实例服务，< 50 万记忆 |
| 容器化 | PostgreSQL | Milvus / ChromaDB | Redis 集群 | 多实例，< 1000 万记忆 |
| 集群化 | PostgreSQL 集群 | Milvus 集群 | Redis 集群 | 企业级，> 1000 万记忆 |

> 本指南数据基于 SQLite + ChromaDB 本地部署的 [storage_growth](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/storage_growth.py) 套件测量。PostgreSQL + Milvus 的实际开销需另行基线化。

## 2. 存储容量估算

### 2.1 单条记忆的存储成本

记忆系统的存储来自三部分：

| 存储组件 | 存储内容 | 估算成本 | 备注 |
|----------|----------|----------|------|
| SQLite | 片段元数据 + 索引 + Outbox + 图谱 + 生命周期审计 | ~1.0 KB/条 | WAL 模式下含 8 张核心表与索引 |
| ChromaDB | 向量嵌入（1024 维）+ HNSW 索引 | ~3.5 KB/条 | 1024 维 × 4 字节 + 索引开销 |
| Redis | TTL 缓存（命中率受 TTL 影响） | ~0.5 KB/条（命中部分） | 仅热数据，TTL 过期后释放 |
| **合计** | — | **≤ 5 KB/条** | 与 [baseline.json](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/baseline.json#L52-L58) 目标一致 |

> 实际成本由 [storage_growth](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/storage_growth.py) 套件精确测量，运行后写入 `baseline.json` 的 `suites.storage_growth.metrics.avg_bytes_per_fragment`。

### 2.2 规模梯度估算表

以下基于 5 KB/条 的理论上界估算（实际通常更低）。**生产部署应以实测值为准**。

| 记忆总量 | SQLite | ChromaDB | Redis（热数据 10%） | 总磁盘 |
|----------|--------|----------|---------------------|--------|
| 1 万 | 10 MB | 35 MB | 0.5 MB | ~50 MB |
| 10 万 | 100 MB | 350 MB | 5 MB | ~500 MB |
| 100 万 | 1 GB | 3.5 GB | 50 MB | ~5 GB |
| 500 万 | 5 GB | 17.5 GB | 250 MB | ~23 GB |
| 1000 万 | 10 GB | 35 GB | 500 MB | ~46 GB |

### 2.3 多租户场景估算

每个 workspace 的存储独立，按用户数 × 平均记忆量估算：

```
总存储 ≈ 用户数 × 平均记忆量/用户 × 5 KB
```

**示例**：1000 用户 × 平均 1000 条记忆 = 100 万条 ≈ 5 GB。

### 2.4 辅助表开销

除 `memory_fragments` 外，以下表会随业务增长：

| 表 | 增长比例 | 说明 |
|----|----------|------|
| `vector_outbox` | ~0（短期积压） | 跨存储一致性桥接，正常情况下被消费清空 |
| `memory_lifecycle` | 1:1 与片段 | 生命周期审计，含 restore/archived 历史 |
| `memory_delete_log` | 0.1:1 | 仅删除操作记录 |
| `memory_merge_log` | 0.05:1 | 仅合并/冲突操作记录 |
| `graph_entities` | 0.1:1 | 平均每 10 条记忆抽 1 个实体 |
| `graph_relationships` | 0.2:1 | 平均每实体 2 条关系 |
| `memory_search_keys` | 1:1 | P1 多键索引，每片段 1 条 |
| `memory_trace_events` | 5:1 | 观测性事件，建议定期清理 |

> 观测性表（`memory_trace_events`）建议配置 7-30 天 TTL，避免无限增长。

## 3. 吞吐容量规划

### 3.1 写入吞吐

参考 [throughput](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/throughput.py) 套件目标：

| 场景 | 单并发吞吐 | 目标 | 备注 |
|------|-----------|------|------|
| 片段创建（含 embedding） | ≥ 50 ops/s | 50 ops/s | ChromaDB HNSW 写入是瓶颈 |
| 表记录导入 | ≥ 100 ops/s | 100 ops/s | 纯 SQLite 写入，较快 |
| 会话抽取（LLM） | 受 LLM 限速 | — | 默认跳过，需独立评估 |

**多并发扩展性**：SQLite WAL 模式下读写不互斥，但写入仍受单写锁约束。实测扩展性参考：

| 并发度 | 预期吞吐 | 扩展比 | 瓶颈 |
|--------|----------|--------|------|
| 1 | 50 ops/s | 1.0x | 基线 |
| 4 | ~150 ops/s | 3.0x | SQLite 写锁争用开始 |
| 8 | ~250 ops/s | 5.0x | ChromaDB persist 频率限制 |
| 16 | ~300 ops/s | 6.0x | 锁争用严重，扩展性饱和 |

> 上述数据为估算，实际由 [throughput](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/throughput.py) 套件实测得出。

### 3.2 读取吞吐

读取主要受向量检索与 SQLite 索引影响：

| 操作 | 单并发预期 QPS | 备注 |
|------|---------------|------|
| 语义搜索（top_k=10） | ~50-100 QPS | ChromaDB HNSW 查询 |
| 混合搜索（4 信号） | ~20-50 QPS | 含 BM25 + 实体 + 时间融合 |
| 图谱邻居查询（depth=2） | ~100-200 QPS | SQLite 索引扫描 |
| 自动召回（auto_recall） | ~10-30 QPS | 含 LLM 调用，受 API 限速 |

### 3.3 容量规划公式

**写入容量**：
```
所需写入 QPS = 峰值用户数 × 平均写入频率 × 业务峰谷比
```

**示例**：1000 并发用户 × 0.1 写/s/用户 × 3 峰谷比 = 300 写/s
→ 需要约 6 并发（按 50 ops/s/并发），建议预留 2x 余量 → 12 并发

**读取容量**：
```
所需读取 QPS = 峰值用户数 × 平均查询频率 × 业务峰谷比
```

**示例**：1000 并发用户 × 1 查/s/用户 × 3 峰谷比 = 3000 读/s
→ 单实例约 200 QPS，需要 ~15 实例（或读副本）

## 4. 资源配置建议

### 4.1 单机开发/小规模（< 10 万记忆）

| 资源 | 建议 | 说明 |
|------|------|------|
| CPU | 2 核 | 单实例足够 |
| 内存 | 4 GB | SQLite cache 20MB + ChromaDB ~1GB + 应用 1GB |
| 磁盘 | 20 GB SSD | 含 10 万记忆 + WAL + 日志 |
| Redis | 可选 | 单实例本地，缓存命中可降低 30%+ 读延迟 |

### 4.2 单机生产（< 100 万记忆）

| 资源 | 建议 | 说明 |
|------|------|------|
| CPU | 4-8 核 | 支撑多并发写入与查询 |
| 内存 | 16 GB | ChromaDB 索引常驻内存约 4GB |
| 磁盘 | 100 GB SSD | 含 100 万记忆 + WAL + 备份 |
| Redis | 必备 | 独立实例，4GB |
| 网络 | 千兆 | 向量同步与 LLM 调用 |

### 4.3 容器化/中等规模（< 1000 万记忆）

| 资源 | 建议 | 说明 |
|------|------|------|
| 应用实例 | 2-4 副本 | 每副本 4 核 8GB |
| PostgreSQL | 主从（4 核 16GB，100GB SSD） | 主写从读分离 |
| Milvus | 独立集群（4 核 16GB，200GB SSD） | HNSW 索引独立扩展 |
| Redis | 集群模式（3 主 3 从，每节点 4GB） | 高可用 + 分片 |
| 负载均衡 | Nginx / Traefik | 按用户 ID 分片，避免跨 workspace 锁争用 |

### 4.4 集群化/大规模（> 1000 万记忆）

| 资源 | 建议 | 说明 |
|------|------|------|
| 应用实例 | 8+ 副本 | 按用户分片 |
| PostgreSQL | 分片集群（每分片 8 核 32GB，500GB SSD） | 按 user_id 哈希分片 |
| Milvus | 集群化（多 collection 分租户） | 单 collection 控制在 1000 万向量内 |
| Redis | 集群（6+ 节点） | 按 user_id 分片 |
| 消息队列 | Kafka / RabbitMQ | Outbox 异步消费，削峰填谷 |
| 监控 | Prometheus + Grafana | P99 延迟 / 错误率 / 存储增长告警 |

## 5. 扩展性瓶颈与优化建议

### 5.1 已知瓶颈

| 瓶颈 | 触发条件 | 表现 | 优化方向 |
|------|----------|------|----------|
| SQLite 写锁 | 并发写 > 8 | 吞吐饱和、错误率上升 | 切换 PostgreSQL；或按 workspace 分库 |
| ChromaDB persist | 大批量写入 | 写入 P99 抖动 | 调大 `batch_size`；或切换 Milvus |
| HNSW 索引膨胀 | > 100 万向量 | 查询延迟上升 | 调整 `ef_construction` / `M`；分 collection |
| Outbox 积压 | 写入 > 同步消费能力 | 一致性延迟 | 增加同步 worker；批量化向量写入 |
| 生命周期审计表增长 | 长期运行 | SQLite 文件膨胀 | 定期归档；配置 TTL 清理 |

### 5.2 横向扩展策略

**按用户分片**（首选）：
- 单实例负责一组 user_id 区间
- 避免跨 workspace 锁争用
- 故障影响范围可控

**按功能分片**：
- 写实例（Outbox 生产）与读实例（向量查询）分离
- 适合读写比悬殊的场景

**混合存储**：
- 热数据（近 30 天）放 ChromaDB
- 冷数据归档至对象存储（S3 / OSS）
- 配合 [smart_forgetting](file:///Users/howdy/pm/agent-memory-system/backend/app/services/smart_forgetting_service.py) 重要性评分自动分级

### 5.3 关键参数调优

**SQLite**（[db_client.py](file:///Users/howdy/pm/agent-memory-system/backend/app/core/db_client.py#L37-L60)）：
```python
PRAGMA journal_mode=WAL           # 已启用，读写并发
PRAGMA synchronous=NORMAL         # 已启用，commit 不强制 fsync
PRAGMA wal_autocheckpoint=1000    # 默认 1000 页，可调大减少 checkpoint 频率
PRAGMA cache_size=-20000          # 20MB，大规模可调至 -200000（200MB）
PRAGMA temp_store=MEMORY          # 已启用
PRAGMA mmap_size=268435456        # 可选：256MB mmap，减少读 IO
```

**ChromaDB**：
- `ef_construction`：建图质量，默认 200，大规模可调至 400
- `M`：图连接度，默认 16，高维数据可调至 32
- `ef_search`：查询质量，默认 100，延迟敏感场景可调低至 50

**应用层**：
- `vector_outbox` 同步批大小：默认 1，可批量化至 50-100 降低 RPC 开销
- `@ttl_cache` TTL：默认 300s，热数据可调至 60s 提升一致性
- 智能遗忘执行频率：默认每 6 小时，大规模可调至每天

## 6. 监控与告警

### 6.1 关键指标

| 指标 | 阈值 | 告警动作 |
|------|------|----------|
| `recall_p99` | > 500ms × 1.2（即 600ms） | 检查索引、ChromaDB 负载 |
| `fragment_create_p99` | > 200ms × 1.2（即 240ms） | 检查 Outbox 积压、写锁争用 |
| `vector_outbox.pending` | > 500 | 增加 worker；批量化同步 |
| `error_rate`（任意操作） | > 5% | 立即排查，可能资源耗尽 |
| `success_rate`（负载） | < 99% | 扩容或排查锁竞争 |
| SQLite 文件大小 | > 估算值 × 1.5 | 触发 VACUUM；检查审计表清理 |
| ChromaDB 目录大小 | > 估算值 × 1.5 | 检查 HNSW 参数；考虑分 collection |
| 内存占用 | > 配置上限 × 80% | 扩容或排查泄漏 |

### 6.2 回归检测集成

将 [L3 回归检测](file:///Users/howdy/pm/agent-memory-system/docs/性能基准报告.md#7-性能回归检测) 接入 nightly/release 流水线：

## 7. 容量规划检查清单

部署前请逐项确认：

- [ ] 估算目标用户数 × 平均记忆量，对照 [规模梯度估算表](#22-规模梯度估算表) 确认磁盘容量
- [ ] 估算峰值写入/读取 QPS，对照 [吞吐容量规划](#3-吞吐容量规划) 确认实例数
- [ ] 选择部署形态（单机/容器/集群），对照 [资源配置建议](#4-资源配置建议) 分配资源
- [ ] 在标准环境运行 [storage_growth](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/storage_growth.py) 套件实测每条成本
- [ ] 在标准环境运行 [throughput](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/throughput.py) 套件实测吞吐，校准扩展比
- [ ] 运行 [load_test](file:///Users/howdy/pm/agent-memory-system/backend/app/benchmarks/performance/load_test.py) 模拟预期并发，确认错误率 < 1%
- [ ] 配置监控告警，接入 [回归检测](#62-回归检测集成)
- [ ] 规划数据归档策略（生命周期审计表、冷记忆归档）
- [ ] 制定扩容预案（用户数增长 2x / 5x / 10x 的应对方案）

## 8. 附录：估算公式速查

```
总存储 (GB) = 记忆总量 × 5 KB / 1024 / 1024
            ≈ 记忆总量 × 0.0000048 GB

写入 QPS 需求 = 峰值用户数 × 平均写入频率 × 峰谷比
读取 QPS 需求 = 峰值用户数 × 平均查询频率 × 峰谷比

所需实例数 = max(写入 QPS / 单实例写入吞吐, 读取 QPS / 单实例读取吞吐) × 余量系数(1.5-2.0)

ChromaDB 内存占用 ≈ 向量数 × 1024 维 × 4 字节 × 1.5（HNSW 索引开销）
                  = 向量数 × 6 KB
```
